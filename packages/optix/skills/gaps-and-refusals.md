# What the tools refuse, and what to do instead

Every line here was met on a live FactoryTalk Optix 1.8.1.27 project through the Studio bridge, and each one is a thing a session otherwise rediscovers by losing a partial write. Read it before authoring a feature you have not authored on this build. Refusals are good news: a refusal that lands before a byte is sent costs nothing, and the ones that land after are the reason this page exists.

## Refused by the bridge, by design

- **An array-valued property.** `GridLayout.Columns` and `Rows` are `String[]`, `AliasNodeArray` is `NodeId[]`: the write comes back `unsupported_array_write` — *"Author array-valued properties in Studio directly."* The trap is that `validate_ops` cannot see array-ness for a node the batch is about to create (the catalogue declares `Columns` as `String`), so a 35-op batch validated `ok`, op 11 was refused, 11 were already on disk, and the batch reported `indeterminate`. `arrayWriteRefusal()` in `lib/index.js` now refuses such a batch before it is sent. **`GridLayout` is never emitted**: its per-cell `GridLayoutProperties` child, created through the bridge's proxy-property route, was the last thing written before Studio died in its own code with `invalid unordered_map<K, T> key` in `HMISolution`. Unequal tracks are two explicit pixel widths inside a `RowLayout`/`ColumnLayout`.
- **`move` on a type.** `not_an_object: UI/Screens/Trend is ObjectType - move handles Object instances (for a variable, recreate it; for a type, it has no layout position)`. Renaming a screen is a re-author: **create the replacement, repoint what mounts it, then delete the old one** — in that order, so nothing dangles mid-batch.
- **`create_object` with `object_type: "ScreenType"`.** Refused. A screen is created with `create_widget {screen:"UI/Screens", name, widget_type:"Screen"}`, which serialises correctly and reports `type:"ScreenType"` in a map.
- **`DigitalAlarm`.** `type_not_found` — it is a Studio menu label, not a type in this build. The qualified name its own refusal suggests (`FTOptix.Alarm.DigitalAlarm`) is refused with the identical message. The authorable route is `OffNormalAlarmController` under `Alarms` with `InputValue` `set_link`ed to a tag.
- **Three logger properties.** `LogVariableTimestamp` and `LogVariableOperationCode` come back `unknown_property` although the bridge's own `valid_properties` names them; `LogMethod` comes back `proxy_only_property` — *"creating it crashes Studio"*. Do not retry these.
- **A `bind` on a `VariableToLog`.** "no settable property 'Value'". `set_link` is the only route, and `VariableToLog` is a **variable kind**, so `create_variable datatype:"VariableToLog"` under the logger is what works.
- **A record limit on a table.** `Table.RecordLimit` exists in the catalogue and no tool writes it, so a bridge-authored store plus logger starts every session with `WARNING (urn:FTOptix:SQLiteStore) [code=1c] … No record limit is set on 'SmtTrend', which may cause an out-of-memory issue on your device`. Set it in Studio, or accept the warning and know it is not yours.
- **A NodeId pointing at a node created in the same batch.** `bad_value: NodeId value must be a resolvable node path`. Point in a second batch; a target from an **earlier** batch resolves fine.
- **`retype` onto a pointer.** `RetypeVariableInline` allows only Boolean, the integer types, Float, Double, String and DateTime. A variable created with the wrong datatype is not repairable — recreate it.
- **`set-structured`.** The bridge has the route (write a placeholder child collection) and no plugin op maps it. Today that means a `VariablesToLog`-style collection is authored one `create_variable` at a time.

## Refused by our own gate, because the bridge let it through

- **A numeric size beside Stretch.** `layout()` throws when a `RowLayout`/`ColumnLayout` child names `Width` or `Height` while that axis's alignment is `3`, because Stretch *is* the size on that axis and the number is discarded. `VIEW-LAYOUT-04` reports the same shape already sitting in a model.
- **A project type named after a built-in type.** `lib/names.js` refuses a `create_type` or a type-bearing `create_widget` whose name is a catalogue type name. Studio generates one global-namespace class per project Screen/Panel/Window/Dialog/Popup into `Private/UITypeDefinitions.cs`, so a screen named `Trend` shadowed `FTOptix.UI.Trend` for every NetLogic in the project. An **instance** named `Trend` is not refused: it generates no class and shadows nothing.
- **`GridLayout` and its cell properties from `layout()`.** `layout()` throws rather than emitting a container the bridge will refuse halfway through.

## What our own playbooks had wrong, and the measurement that fixed it

- **A script pointer's datatype is `NodeId`, never `NodePointer`.** `NodePointer` reaches the bridge as `BaseDataType`, the `Value` coercion switch never reaches its `NodeId` case, the path stores as a String, and the runtime fails at `Start()` with `InvalidCastException: Unable to cast object of type 'System.String' to type 'UAManagedCore.NodeId'` (`code=df0003`). `IUAVariable.Value` hands back a `UAValue`, so `(NodeId)pointer.Value` inside a `try/catch` *is* the read.
- **`Convert.ToInt32(value.Value)` does not compile** on this build (`CS0121`, ambiguous between the `bool` and `DateTime` overloads, because `Value` is `dynamic`). Write `int current = value.Value;`.
- **The node type is `UAManagedCore.IUANode`, not `Node`** (`CS0246`), and folder children are `.Children`, not `GetChildren()`.
- **`ALIGN.TOP` does not exist.** On both axes 0 is LEFT; a numeric track under a layout parent needs `0`, a filling track needs `3`.
- **Trend pens are not reliably created disabled.** In the measured `AdvancedTrendMain` all four arrived enabled. Look at the preview before writing code to switch them on.
- **The shipped alarm grid's state columns are readable.** Each is a `<div data-column-index="4|5|6">` wrapping an `<img>` whose `src` names the state (`RadiobuttonDarkEmpty.svg`/`RadiobuttonDark.svg` for Active, `ApplyDark.png`/`CloseDark.png` for Acked/Confirmed), so an acknowledge is provable in a preview — through the grid's own button, never through `optix_invoke` (`No behaviour or observer found that handles the method 'Acknowledge'`).
- **A screen's box is its mounter's declared box, unclamped.** The checking tools used to compare a screen against the *window* and to invent a clamped box the runtime never hands out. Both are fixed; a screen that overflows its host is now named as an overflow.

## Operational traps that report success while nothing moved

- **A bridge write is not durable until `optix_save`.** A Studio crash is a clean rollback, not a half-written project: a `Width` change made moments before a crash left no trace anywhere under `Nodes/`.
- **The runtime serves the saved project.** A `.cs` edit needs a build with the **runtime stopped**, or the build fails with `MSB3027/MSB3021 … locked by "FactoryTalk Optix Runtime 1.8.1.27 (<pid>)"`. A design-only change needs only a save — and `build_state.state "stale"` afterwards is expected, because Studio regenerates `Private/UITypeDefinitions.cs`.
- **A NetLogic loads when its panel is instantiated.** A clean startup log proves nothing about a widget's logic; open the screen that hosts it.
- **A NodeId's namespace index is session-local.** The bridge echoed `102/<guid>` and the runtime logged `9/<guid>` for the same node. Compare the Guid body, never the index.
- **WAL mode makes a store-file size poll lie.** The main file stayed at 4 096 B while its `-wal` grew to 4 144 752 B. Copy the file before reading it — the runtime holds a lock.
- **An alarm whose source tag is written fast re-raises on its own poll** (~12 s measured, against a 30 s logic write), so an acknowledge does not persist. Prove it as a state pair against one row's timestamp.
- **`needs_save.pending` is held by the plugin and survives a Studio crash.** Clear it with `optix_status saved:true` after the engineer confirms the save; `optix_build` refuses to run while it stands, and `optix_emulator restart` reports a self-contradictory `save_verdict` because it compares against the *first* pending change.
- **`validate_ops` does not resolve `object_type`.** `NotARealTypeAtAll` validates `ok`; it does check existence for a `create_object` (`already_exists`). And `set_link` is answered `unknown_op` by this bridge build — that is an **unchecked** op, not a refusal, and a completed batch reports it in `unchecked`.
- **One bad op refuses a whole batch** (`applied 0`), which is the behaviour you want; a refusal *mid*-batch is what `arrayWriteRefusal` and the name gate exist to prevent.
- **A tool whose schema the DSL refuses silently disappears.** `pointers.items.required` was rejected as `UNSUPPORTED_SCHEMA … not supported by the value schema DSL`, which would have dropped `optix_script` from the booted plugin, and the full test gate could not see it. `test/optix-tool-registration.spec.mjs` is what makes that visible.
- **Two diagnostic tools do not work in this build.** `optix_logs` fails with `value is not lossless JSON` and `optix_screenshot`/`optix_preview` fail with `Cannot read properties of undefined (reading 'playwright')`. Read the runtime log file directly (open it with `FileShare.ReadWrite` — the runtime locks it) and drive the preview with the browser tools.
- **The installed plugin is not the working tree.** A change under `packages/optix/lib` is not in the live `optix_*` tools until the plugin is rebuilt and reinstalled; prove a new rule live through the working-tree harness, and say which one answered.
- **The runtime runs in demo mode** and closes itself after 120 minutes. Adding a DataLogger took the licence line from 5 to 6 Standard Feature Tokens (Native 1 + Web 3 + Alarm controller 1 + Data logger 1) — demo mode still runs it, a real device would not.

## One cosmetic residue, diagnosed rather than fixed

`CHANGELOG.md` carries 445 corrupted runs across 76 historical lines (`### Fixed ÃÆ’Ã†â€™…` where an em dash belongs, `1280Ã—800` for a multiplication sign). It was introduced in one commit, `ab5fe6011` (2026-10-28, *"Add headless alarm snapshot and decode alarms during export (0.22.0)"*, 99 marker sequences; its parent had none), and compounded to 7 032 because every later edit re-encoded text that was already corrupted. `scripts/repair-encoding.mjs` refuses it — every undo layer yields U+FFFD — and a forward-corruption model of 50 candidate punctuation characters over 6 layers matches **0 of 445** runs, because the runs begin with `¡` (U+00A1), which a pure UTF-8→cp1252 chain of punctuation never produces. The file holds **no** U+FFFD, and a scan of 2 260 textual files repo-wide found **no file carrying one**, so no code or live documentation string is lossily encoded: this is historical prose, and rewriting it would be guesswork. The rule that keeps it from spreading is the one that caused it — never let text round-trip through a console that decodes as cp1252, and never put mojibake literals on a command line.
