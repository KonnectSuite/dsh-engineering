What this bundle is

Explain what the engineering bundle adds to AryaCode, how rows and components fit together, and which surfaces this handbook covers.

Audience: Readers new to the bundle

One install, many surfaces

@aryacode/dsh-engineering is one AryaCode plugin bundle. It adds engineering tools to the agent's toolbox and the matching preview surfaces to the workbench: a ladder viewer, FactoryTalk View displays, Optix screens and a read-only drawing pane. A compatible AryaCode profile mounts the bundle; the bundle then composes the products it ships.

The source repository is KonnectSuite/dsh-engineering. Nothing in the bundle edits the installed AryaCode app or the installer payload. Rows load at boot, and every write lands in a workspace the user chooses.

Rows and components

A row is one entry in the bundle patch, cordis.patch.yml. Loading a row loads a component, and there are two shapes:

  • Product rows mount a whole product: tools, a skill, and previews when the product has a preview.
  • Support components mount one smaller thing: the engineering resources corpus, the document previews, and the migration machinery.

Every component is described in components.json: default posture, maturity, tool count, skill budget, the evidence gate, and the documents that own it. The manifest and the patch are checked against each other in test/components.spec.mjs, so a row that exists in only one of them fails the suite.

What ships switched on

The patch ships most rows on. At 0.103.0 two rows, ECAD (12 tools) and PLC-5 (8), shipped switched off: their tools were compiled and tested but did not add to a fresh install's default context or profile. A switched-off row is unloaded, not hidden, until a profile switches it on. This change retires the ECAD product row - its read-only drawing preview moves to the previews surface - and adds a read-only SLC 500 row (10 tools, slc500_ namespace), which also ships switched off.

Every row adds a slice of tool schemas to the model context. components.json records a default-on budget (defaultOnTools, defaultOnSchemaCharacters) so a release cannot quietly grow the context a fresh install pays.

Maturity

Every component is beta. In this bundle that means tested, with a stabilityNote that states exactly what is not proved. The component reference, docs/reference/components.md, owns the field definitions and the checks. This handbook describes what a session feels like; it does not replace that reference.

How to read this handbook

  • Chapters 2-11 cover the shared loop and each product.
  • Chapters 12-13 cover previews, safety and approvals.
  • Chapters 14-15 cover troubleshooting and what is not proved.

Where a chapter names a measurement, the figure comes from the repository's recorded evidence (docs/capabilities.md, the product pages and HANDOFF.md). Anything not recorded there is marked unverified, and a claim that has not been measured on the current host stays a claim.

How a session works

Describe the shared loop, the read/write gate, and what a result can and cannot prove.

Audience: Anyone starting a first session

The five surfaces

A session has five kinds of surface, shared by every product:

  1. Tools the agent calls, grouped by job: read, draft, verify, and where a product allows it, a gated write.
  2. A skill, loaded when the product is involved, that states the order of work and the product's own rules.
  3. A capability or status probe that reports what is installed and reachable before any claim is made.
  4. Documentation tools that look up installed help and authored pages, without shipping vendor bytes.
  5. Preview faces in the workbench that render a local file; they do not launch vendor software.

Inspect, decide, call, verify

  1. Inspect. List what exists before acting: projects, apps, displays, screens. A capability or status tool reports the installed software and any missing piece.
  2. Decide. Pick the smallest tool that answers the question. Reading is the default; a draft is a new file, not an edit in place.
  3. Call. Tools return an envelope. On success it carries the result; on failure it carries a code, a message, and a fix. A refusal is information, not an error to work around.
  4. Verify. Trust the vendor engine, not the agent's intent. A Studio SDK build, a re-export from Studio, a MotionWorks compile, an Optix build or a schema validation is proof that the artifact was accepted. "The tool ran" is not proof.
  5. Hand off. Where Studio or the IDE must act, produce a plan the engineer can follow, then stop.

Read-only and write gated

Every product has a read path that needs no license and touches no project: parse a file, render a display, search installed help. Write paths are narrower:

  • A draft tool writes a new artifact beside the source and refuses to overwrite.
  • An apply or save tool is a gated write with per-call approval. If the session policy cannot ask for approval, the call returns APPROVAL_UNAVAILABLE and nothing is written.
  • A few writes go to a device or IDE. Those are the most gated and are never the default.

Read-only rows are read-only by construction: they ship no write tool and no write switch. A profile switch can remove a capability; it cannot add one the build does not carry.

What a result proves

A green check proves the artifact passed that check. It does not prove the line will run on a controller, the screen is safe to deploy, or the vendor would accept the project. Every entry on the workbench is a preview, not a replacement for the vendor's own environment. For a claim about behavior, the evidence is a test or a recorded measurement, and the evidence page (docs/capabilities.md) says which image proves what and — more importantly — what an image cannot prove.

Where your work lands

  • L5X: drafts are new .L5X files; an SDK build creates a new ACD and records the source hash.
  • FactoryTalk View: a draft is a new ME export folder; the batch import XML is validated, then Studio imports it.
  • Optix: the file channel writes the saved project; only one save is automated, and one build remains a human action.
  • MotionWorks IEC: a staged copy is edited; the real project is backed up on open.
  • Migration / PLC-5 / SLC: reads only, or a report written to a new file.

Studio 5000 L5X

Cover the offline-first L5X workflow, revision guards, SDK builds, and the controller boundary.

Audience: Controls engineers reviewing or drafting L5X

What the row does

The L5X row is the largest product surface; the generated tool reference counts its tools and is the count of record. It reads, reviews, drafts and (with the SDK) builds Studio 5000 projects. It is offline-file by default: open an .L5X export, inspect it, review it, draft a change, and compile a new ACD where Studio and the SDK are installed.

No install is needed to read, review or draft. The SDK build needs a licensed Studio 5000 installation with the Logix Designer SDK, and a live-controller session needs an address and an approval.

Open, inspect, review

The first call is l5x_open_project, which returns a project_id for the rest of the session. From there: l5x_project_overview, l5x_list_components, l5x_get_component, l5x_find_references, and l5x_run_checks with the bundle's own rule set (43 rules at 0.103.0: unused tags, scheduling, undocumented logic, latches, multiple writers, instruction problems, FBD wiring, SFC charts, refused rungs, safety placement). The rules are ours, not a vendor sign-off; a clean run means this rule set found nothing.

Ladder previews and routine diagrams read the project's neutral text. They are views of the file, not an emulator.

Revisions and the two guards

The row is revision-aware. It reads .L5X from revision 19 upward. Revisions the build has seen are marked known; any other revision opens with the verification note untested_revision; below 19 the file is refused with UNSUPPORTED_REVISION. An ACD goes through the SDK, which supports revision 31 and up.

Two documentation-tool guards keep revision lookups honest:

  • REVISION_REQUIRED — a revision-sensitive question named no revision, so the tool asks for one instead of silently serving the newest shard.
  • INSTRUCTION_NOT_IN_REVISION — you asked at a revision where that instruction or page is not recorded; the tool refuses rather than serve another revision's text.

A page with no revision evidence comes back with revision: null; the tool does not imply it matches. If a lookup is revision-sensitive, name the revision.

Drafts and the build boundary

Draft tools (l5x_draft_rung, l5x_draft_tag, l5x_draft_validate) work on one new .L5X beside the source; l5x_draft_apply writes that file and refuses to overwrite. Paste it into Studio yourself. l5x_build_acd_from_draft compiles one new ACD from a draft with the offline engine: revision 37 and up, one existing RLL or ST routine, refuses new routines, tag changes, safety and protected routines, and takes roughly 18-26 seconds on the recorded host. On Studio 5000 v36 the engine refuses Build with "Operation not supported on Logix Designer version 36.0".

l5x_verify_offline_l5x expects a Studio-exported L5X. l5x_export_acd_to_l5x can produce a file Studio refuses to re-import (XMLSrv_E_IMPORT_ABORTED_NO_CHANGES, observed 2026-10-23); treat it as an export for reading, not a round-trip.

The controller boundary

Controller tools upload, read mode and tags, change mode, and download. Each is approval-gated per call. Live writes validate the tag and read it back; a mismatch returns WRITE_NOT_VERIFIED. A download needs a verification_id for a build from the same chat and both hashes unchanged. Live work is the operator's decision, not the agent's default.

What this row will not claim

All reads are static. The 43 rules are not a vendor sign-off. Instruction, revision and controller coverage beyond the recorded 37.11 verification is unmeasured. FBD and SFC execution semantics are not exercised. And no offline artifact proves a machine's online logic is safe or matches the export.

FactoryTalk View ME and SE

Read ME exports, author displays against the installed schema, prove an import, and know where SE help fits.

Audience: HMI engineers

The product row

FactoryTalk View ME is a product row; the generated tool reference counts its tools and is the count of record. Its read path works on a Studio ME text export: it copies the display XML, the HMI tag CSV when Studio exported one, and the alarm XML into a new folder, then reads them. It never decodes the native .med/.mer, never contacts a PanelView terminal, and never launches Studio to answer a read.

The row needs Studio ME on Windows for three things only: listing applications, producing an export, and the import wizard at the end. A read session needs just an export folder. SQL Server Express and sqlcmd are optional, for tag snapshots. Chrome or Edge is needed only for PNG rendering; SVG needs none.

Where SE help fits

FactoryTalk View SE is not a separate product row in this bundle. Its installed help is a documentation source: the knowledge plane indexes the SE help pages that Studio installs and parses their bodies locally when a documentation tool reads one. Nothing from the SE help tree is shipped, and a missing SE install produces SOURCE_NOT_INSTALLED, not a broken page.

First session

  1. ftview_apps lists the applications Studio knows.
  2. ftview_export copies a fresh export into a new folder and records whether the alarm and tag files are fresh, stale or missing.
  3. ftview_open opens the export; ftview_check looks for unbound tags, missing images and alarm setup problems, and lists checks it did not run.
  4. ftview_object_types reports the schema versions installed; ftview_render draws displays to SVG and, with a browser, PNG, reporting objects off-canvas or overflowing.

Draft, import, prove

Draft tools write a new export folder. A draft writes the schema attributes the export declared - ME 17 in the recorded case; an ME 10-16 display declares a different Gfx-ME*.xsd, so validation reports the declared version first and refuses to pretend it is ME 17. ftview_apply writes text files only; it does not rewrite binary Images/.

To get the draft into Studio: ftview_studio_handoff returns the ordered steps, the Studio Graphics Import Export Wizard imports BatchImport_<app>.xml, and ftview_verify_import re-exports and compares the imported result object by object. Building the .mer and downloading it to a terminal remain Studio steps.

Limits recorded at 0.103.0

  • One ME export has been measured on the recorded host; other ME versions, a second application, PanelView terminals and the Studio import step remain unmeasured.
  • The alarm decoder reads 34 of 66 applications measured on that host; the rest fall back to the wizard snapshot and write the reason into export warnings. Tag decoding succeeds on 64 of 66.
  • The ApplicationManagerServer backup path fails with "Class not registered" for ME, so the bundle claims no ME backup.
  • ftview_check is structural, not an XSD validation.
  • A missing alarm or tag file means the export did not carry it, not that the application is broken.

What this row will not claim

It will not decode native project files, touch a terminal, automate the Studio import, or promise that an export copied yesterday describes the application running today. The snapshot's age is reported, and stale means stale.

MotionWorks IEC

Explain the IDE-bound MotionWorks workflow, its backup rule, and the honest state of verification on this host.

Audience: Engineers with a MotionWorks IEC installation

The product row

MotionWorks IEC is a 24-tool live-IDE row. It reads and edits a project through the MotionWorks automation bridge: one session is opened per chat and the rest of the calls carry its handle. It never automates windows; a handful of desktop-only actions are handed to a computer-use companion with a stated step.

The row needs MotionWorks IEC 3 Pro on the 3.x line (3.0.3–3.7.5), a licensed IDE that is running, Windows, 32-bit PowerShell with the vendor automation components, and a Python 3 interpreter (MW_PYTHON overrides the one it finds; without one the call returns PYTHON_UNAVAILABLE).

The staged copy rule

MotionWorks edits a real project in place once saved, so the row never starts there:

  1. mw_project_find finds the project; mw_ide_status reports the IDE.
  2. mw_project_stage writes a copy under .motionworks/stage and the session works on the copy.
  3. mw_project_open takes one verified backup of a real project under the shared backup tree before opening it.
  4. Edits go through mw_edit_code, which returns the body hash, then mw_validate, mw_compile, mw_diagnostics and mw_verify against a baseline. mw_apply saves the open project in place, with the backup as the undo.

The compile verdict is the vendor engine's, not a runtime test. Downloading to a controller is not part of this row.

The verification gap on this machine

This host has no MotionWorks IEC installation with a reachable IDE bridge. The repository records live evidence for the 3.x line (3.0.3–3.7.5) against a staged copy of a real project on 2026-10-23, but that evidence cannot be reproduced here: on this machine the compile, live-IDE and profile paths are unproved. They are fixture-tested only - the automation contract, the session handling and the backup rules have tests, but no project has been edited on a running IDE on this host.

Treat every MotionWorks claim in this handbook as a claim about tested code, not about a project this machine edited. The capability page states the same in docs/capabilities.md.

What this row will not claim

  • That other MotionWorks IEC versions, controller families, downloads or a real-workspace write path work: none of those were measured.
  • That a compile proves a program runs: the vendor engine accepts it; runtime needs a controller.
  • That the IDE can be skipped: it must be running, licensed, and connected to the bridge.
  • That the bundle supplies a house style for MotionWorks: it does not in this release.

FactoryTalk Optix and NetLogic

Work on a live Optix model through the Studio bridge, dry-run first, and never mistake a saved project for a build.

Audience: Optix engineers

The product row

FactoryTalk Optix is a 32-tool live-IDE row. Its bridge is a small C# NetLogic class that the bundle writes into the Studio project and the engineer loads in Studio. The bridge answers on loopback HTTP; the bundle does not run the upstream MCP server. optix_bridge_arm writes the bridge into ProjectFiles/NetSolution and backs up the previous files first.

The row needs Optix Studio 1.8.1 (the repository records 1.8.1.27), a running Studio with the project open, and - for the bridge only - the .NET 8 SDK. The bundled dotnet is a runtime; it cannot compile the bridge. Tesseract is optional, for OCR of screenshots, and Chrome or Edge is needed for preview.

Two things no tool does

No tool can compile the bridge class, and no tool can run StartBridge. Both are Studio actions: the engineer opens the .optix, builds the project, right-clicks StartBridge and answers the Studio security prompt with Proceed. Until then the bridge tools report that the bridge is not reachable.

That is deliberate. The bundle's tests do not pretend to replace a vendor IDE step.

Three states, and save is not build

Optix has three states and the row keeps them apart:

  • live model - the model Studio has open, read through the bridge;
  • saved project - what is on disk after optix_save, which alone raises the Studio window for one Ctrl+S and refuses if the foreground cannot be taken;
  • rendered screen - optix_preview/optix_screenshot render what the saved project says, not what an unsaved buffer says.

A save is not a build. Measured on 2026-11-18, a save moved 29 sources while the compiled DLL's timestamp stayed older; an unchanged build can mean the build did not run, not that the change is equivalent.

The seven phases

Brief, scaffold, open and arm, connect, author, persist, look and release. Tools are grouped the same way: session (optix_status, optix_bridge_arm), read and research, authoring and screens, NetLogic scripts, project and build, preview, and release. optix_read is the evidence gate: it reports what the bridge sees before a claim is made.

Writes default to dry_run; the switches allowWrites, allowDestructive and allowInvoke gate the real ones. The file channel refuses to write while a live session has unflushed changes, and it refuses a second writer. An apply is all-or-nothing and keeps .dsh-backups.

What this row will not claim

  • That an empty .optix can be created: none of the tools does that; start from a template.
  • That the project can be built from the bundle: build is Studio's.
  • That a saved project is a running screen: the emulator preview is a preview.
  • That screenshots prove behavior: an image cannot prove a click works.

Legacy migration

Assess a legacy project against a target, lint it, compare it, and report - with the wizard's boundary stated.

Audience: Migration engineers

The product row

Migration is a support row (7 tools at 0.103.0, plus migration_docs in this change) that turns a legacy control project into a reviewed migration story. It reads .L5K, .SLC, .RSS, .ACH, .RSP and .L5X inputs, assesses them against a five-decision plan, lints ladder, compares expected with real logic, and writes a report. It never drives Studio and never contacts a controller.

One tool starts another program: slc_read opens RSLogix 500 or 5 hidden, reads, and closes without saving. Everything else parses files. .SLC text exports and .L5K files need neither vendor application.

The workflow

  1. migration_plan records five decisions - target CPU, target revision, I/O strategy, HMI scope and acceptance - across eight stages in .migration/plan.json. It refuses to advance while a decision is unanswered.
  2. migration_assess reads the project and reports scope, instruction use and risks. An imported .L5X gets the wizard-defaults audit; a native .L5X is refused with ALREADY_LOGIX.
  3. slc_read reads a project through the vendor server when the input is .SLC/.RSS/.ACH and the tools are installed.
  4. l5k_lint flags structural problems (TRAILING_COMMA, DUPLICATE_TAG, TAG_NAME_TOO_LONG, ROUTINE_PAREN, ROUTINE_UNBALANCED, PLACEHOLDER_TAG, INDIRECT_ADDRESS, REVISION_BELOW_TARGET, BOM).
  5. migration_compare compares expected and real logic and separates expected differences from real ones; a terminal END rung is not logic.
  6. migration_resolve proposes resolutions with citations; it never writes.
  7. migration_report writes Markdown or .docx to a new path.

The instruction map cites the vendor manuals it draws on; it is a reading aid, not a licence to claim a conversion is safe.

The wizard boundary

RSLogix 500's Project Migrator, and RSLogix 5's equivalent, cannot emit a project newer than the wizard ships - version 30-31 for RSLogix 500 and 30-32 for RSLogix 5 in the recorded material. So an imported project must be retargeted in Studio 5000 to revision 37 or later before an offline build proof is meaningful. The wizard's I/O choice is Keep Existing or Update All; modules that cannot convert take a PLACEHOLDER_TAG, and leftover ?/PCE addresses are recorded as review items rather than silently fixed.

Recorded coverage

Four projects were measured: Slitter 8 (3,409 symbols and 209 data files, 1,398 of 1,426 rungs matched, 259 indirect addresses), an EN049 PLC-5 project (34 files, 306 of 320 rungs, 90 data files, 131 indirect addresses), the EN049 marker census (214 sites, 201 answerable, 35 for review), and SLITTER10 .RSS (15 markers across 55 rungs).

What this row will not claim

  • That every legacy instruction converts: the map covers 58 mnemonics with citations, and uncovered instructions are review items.
  • That a comparison result equals acceptance: migration_resolve proposes; a person approves.
  • That the wizard's output is build-ready: retarget first, then prove the build.

RSLogix 5 and PLC-5 reads

Read a PLC-5 project through RSLogix 5 or the container parser, and know what remains unread.

Audience: Legacy PLC-5 engineers

The product row

PLC-5 is a product row: 8 read tools at 0.103.0, with a documentation tool and six more read tools in this change. It ships switched off. It is read-only by construction: there is no write tool, no write switch and no controller session.

The row has two independent read paths:

  1. Vendor automation - RSLogix5.Application, a 32-bit local COM server driven from 32-bit PowerShell. The server is opened with Visible=False and PromptForRevNote=False, and every exit calls Quit(0, false) so no hidden instance is left behind. The server is single-instance, so a stray hidden RSLGX5.exe can make the next open fail with CO_E_SERVER_EXEC_FAILURE; the error names the process to end.
  2. Container parser - a dependency-free reader for the .RSP OLE2 compound file. It answers without RSLogix 5 installed, but it knows less.

Both paths were measured on one project, F00607.RSP, through RSLogix 5 v10. Other versions, SFC and sequential files, and point-card part numbers were not tested.

What a read reports

plc5_open returns the project inventory measured for that project: 52 program files, 2,168 rungs, 226 data files, 4,189 symbol records, 10 configured chassis and 443 I/O cells. The container named the same project and processor (MML10PF3PX3R9) and its route (045_VIM\10.164.108.113\Backplane\1\CH A\1) across 53 streams and 38 ladder files.

Three inventories, and they deliberately do not pretend to be one:

  • configured chassis - from the project configuration;
  • point cards - not recorded in this project, so absent rather than empty;
  • referenced addresses - what the logic actually names.

The gap between the second and third is a finding, not a bug.

What a read does not prove

  • Data-file values are not readable through these paths, so tag values are out of scope.
  • No online state: the row reads a saved file and never contacts a controller.
  • No point-card part numbers: a configured chassis is not a bill of materials.
  • The container's answer says it knows less: its coverage reports coverage.unverified, and the read-only contract is only as strong as the recorded project.

Treat a PLC-5 read as evidence of what the file says, not of what the machine does.

SLC 500

The new read-only SLC 500 row: what it reads, what it needs, and what is not proved yet.

Audience: SLC 500 engineers

The row

The SLC 500 row is new in this change and ships switched off. It is read-only by construction: ten tools in the slc500_ namespace and a rslogix-500 skill, with no write tool, no write switch and no controller session. It never edits a project, never writes an .RSS, .SLC or documentation export, and never goes online to a processor.

The read paths

  • Text export. An .SLC text export is the neutral-text path and works with no RSLogix 500 installation. The tools parse it for processor identity, program files, ladder rungs, data-file layout and referenced I/O addresses.
  • Documentation export. An RSLogix 500 documentation export (.EAS, .ERP, .EIC, .ESG, .CSV) is the highest-fidelity machine-readable description of symbols, addresses and comments. The text export truncates symbols to 15 printable ASCII characters; the documentation export keeps the full symbol and description, so a cut-off symbol is a prompt to ask for it.
  • Binary .RSS. Reading the binary container needs the RSLogix 500 automation server, and only the Professional or Developer edition exposes the read methods. When the server is absent the answer is SOURCE_NOT_INSTALLED; when it is registered but the edition or a transcript is missing the answer is NOT_LICENSED. A redacted transcript fixture proves the boundary, not a live vendor session.
  • .ACH. APS-era material is detected, named and refused; re-save it from the era's tool or export a text version. No best-effort decode.

The ten tools

slc500_capabilities reports what the host has; slc500_open opens a project path and returns identity and inventory, optionally comparing a second source; slc500_ladder reads one program file's rungs in neutral text; slc500_find searches symbols, data-file values and rung text; slc500_io_census counts referenced I/O by rack/slot cell, word and bit; slc500_io_config reports the processor chassis and modules or the honest limitation; slc500_data_read returns a value window from one data file; slc500_processor reads identity and status words; slc500_database parses a documentation export into address, symbol and description rows; slc500_docs serves the authored knowledge collection through the five documentation actions.

Limits stated plainly

  • The text export does not carry point-card identities, wiring or analog scaling. What it does not prove is reported under coverage.unverified, never filled in.
  • Status words are read from the file or automation snapshot and explained by a slc500_docs page; the row does not recite a bit table from memory.
  • When two sources disagree - a binary read and a text export, or two exports - the row returns both values and names both paths. A conflict is evidence to show the operator.
  • The row describes SLC 500 semantics; it does not convert a project. Conversion belongs to the migration row, which owns the plan and the report.

What is not proved yet

The parser and the automation boundary are covered by repository fixtures, including a redacted transcript. A full project read from an owner-licensed RSLogix 500 session is still the evidence that closes real-project coverage; until that transcript exists, treat the parser's coverage of an unfamiliar export as unproven rather than assume it. The product page owns the definitive scope once the row is wired into the release; this chapter describes the row as built.

Engineering resources

Use the authored standards corpus and the profile extractor without mistaking judgement for vendor text.

Audience: Reviewers and style reviewers

Two tools, two jobs

The engineering resources row carries two tools:

  • engineering_reference searches the authored corpus. It has four ways in: contents, query, id and domain.
  • engineering_profile extracts a style profile from an L5X project (project_id) or a FactoryTalk View ME view (view_id).

Both work locally. No model, no network and no vendor document is consulted at call time.

The corpus

The corpus is 70 Markdown pages with 233 rule IDs across 8 domains: IEC, Rockwell, migration, Yaskawa, view, Optix, HMI and craft. A page declares its id, title, domain, level, basis, tags, target products and the rules it states; rule IDs are unique and follow <AREA>-<TOPIC>-<NN>.

The levels are intro, practitioner and specialist, and the corpus is deliberately small: it is judgement, written in the repository's own words and citing the standard or practice it rests on. It reproduces no standard text; the content licence is packages/resources/LICENSE-CONTENT.md.

Search ranking is deterministic and local: exact rule or title matches first, then tags, then substring, then a body scan. The generated index is built by scripts/gen-resources.mjs (pnpm resources:build), and pnpm resources:check fails when it is stale. Front matter, domains, levels, rule IDs and size budgets are validated; a page over 900 words or 12 KB fails.

The profile

engineering_profile reads naming, idiom, HMI and comment habits plus evidence, confidence and source fields. It is extracted only from L5X and FactoryTalk View ME today; Optix and MotionWorks are not covered. The profile can be passed into the FTView display-drafting tools as a style input - it is a suggestion set, not a rule the vendor enforces.

What these tools will not claim

  • They return pages and profiles, not answers. A page states what the repository's practice is; it is not a vendor specification.
  • A clean profile is not a review. It describes habits; it does not judge whether a line is correct.
  • The corpus is not exhaustive: a missing topic is a gap in the authored set, not evidence that no rule exists.

Documentation tools and the knowledge plane

The five documentation actions, the licensing posture, and the revision rules that keep lookups honest.

Audience: Anyone looking up a vendor manual through the agent

The idea

Every product row that has a documentation surface exposes a documentation tool: l5x_docs, ftview_docs, migration_docs, plc5_docs and, with the SLC 500 row, slc500_docs. The tool answers five actions and nothing else.

The five actions

ActionQuestion it answersResult
contentsWhat collections are there, and what sections does one have?Collections with page counts, source kind, revisions and readiness; or a section table of contents.
searchWhere is this topic discussed?Up to 8 hits with id, title, section, score and a short snippet.
readGive me the page.The page text (up to 8,000 characters) plus source and revision fields.
statusIs this collection usable here?Ready, index-only or absent, with the installed root and page count.
lookupIs this identifier defined?Exact identifier matches with the pages that define them.

Errors are part of the contract: INVALID_ACTION, QUERY_REQUIRED, NOT_FOUND (with the closest ids), SOURCE_NOT_INSTALLED when the vendor help a collection describes is not on this machine, REVISION_REQUIRED when a revision-sensitive question names no revision, and INSTRUCTION_NOT_IN_REVISION when the named revision does not carry the page. A failed call names a fix.

Licensing posture

The line is firm and easy to state:

  • Authored pages ship. They are written in the repository's own words and may be redistributed.
  • Vendor help is never shipped. A committed index carries ids, titles, sections and paths only - metadata, not page bodies.
  • A read of installed help happens locally, at call time, against the vendor help installed on the machine. If the help is missing, the call reports SOURCE_NOT_INSTALLED; it does not substitute a cached copy.
  • No network call is made to answer a documentation question.

This is why the bundle can search a 5,500-topic Studio 5000 help tree without carrying its 200 MB into the package.

Revisions are not a footnote

A documentation answer that silently serves the wrong revision is worse than no answer. The tools therefore:

  • accept an optional revision on search and lookup, and never silently fall back to the newest shard when a revision was named;
  • return REVISION_REQUIRED when a revision-sensitive question names no revision, instead of implying the newest one matches;
  • refuse with INSTRUCTION_NOT_IN_REVISION when a requested page or instruction is not recorded at the named revision;
  • return a page whose index carries no revision with revision: null, rather than implying it matches.

The engineering resources corpus is a separate authored surface: engineering_reference remains the standards search tool, while the product documentation tools serve vendor-manual lookups.

What the tools will not do

They will not answer a question the indexed text does not contain, will not fetch a manual from the internet, and will not decide whether a page applies to the project in front of you. That decision stays with the engineer.

Drawing and display previews

What the viewer surfaces show, what they do not prove, and what changed when the ECAD product row retired.

Audience: Anyone using the workbench previews

Three preview faces

The workbench has three engineering preview faces, each rendering a local file:

  • Ladder viewer - a routine rendered from L5X neutral text, with contacts, coils and branches laid out for reading.
  • FactoryTalk View display - a display rendered from the ME export XML, including the object bounds the exporter wrote.
  • Drawing pane - a read-only electrical drawing preview for DXF/DWG files: drag to pan, wheel to zoom, layout tabs, a layer panel, text search, a coverage badge, print, and SVG or PNG export.

A fourth, the settings face, reports the bundle's configuration. Optix screens are previewed through the Optix row's emulator and screenshot tools rather than a separate workbench face.

The ECAD change

The ECAD product row is retired in this change. Its drawing pane remains as a preview because reading a drawing is still useful; what leaves is the product surface - the deliverable tools and their editing-adjacent workflow. Electrical authoring stays with AryaCAD Electrical, which the owner runs separately; the bundle does not create or edit drawings.

If a session needs drawing tools and the ECAD row is off or absent after this change, that is expected: the viewer is not the row.

What a preview proves

A preview proves that a local file parsed and rendered. It does not prove:

  • that the file came from the machine that is running now - an export has an age;
  • that the drawing is correct, current or approved;
  • that a display will deploy to a terminal;
  • that a rendering matches the vendor runtime's rendering.

For display behavior, the vendor runtime is the evidence. For a drawing, the issued file is. An image is a reading aid; docs/capabilities.md records which images were captured and what they cannot show.

Practical notes

Previews are read-only by construction: they open a file and produce an image, and never write back into it. Renders that need a browser report clearly when Chrome or Edge is missing instead of producing a blank image. Both workbench faces follow the host's theme tokens, so light and dark themes show the same content.

Safety, approvals, and where work happens

The write gate, the approval rules, the backup tree, and the rule that keeps the installed app untouched.

Audience: Operators, approvers and reviewers

The default is read

Every product starts read-only. Reading a project, rendering a display, searching installed help and reading a saved project file are all safe in the sense that they write nothing. A write happens only when a tool named for writing is called, and only when its gate is open.

Read-only rows (PLC-5, SLC 500) are read-only by construction: no write tool, no write switch. A profile cannot add a capability the build does not carry.

The write gate

A write path passes through these controls in order:

  1. A draft, not an overwrite. Draft tools write a new artifact beside the source and refuse to replace an existing one. Output paths that already exist are refused unless the tool explicitly allows an overwrite.
  2. An explicit apply or save. The draft must be applied or saved by its own tool call; nothing writes on the way past.
  3. Per-call approval. A gated write asks for approval for this call. When the session policy cannot ask - a non-interactive run, for example - the call returns APPROVAL_UNAVAILABLE and nothing is written. Approval design assumes a person sees what is about to happen.
  4. A verify step. Where the product has a vendor engine, the result is verified by that engine, not by the bundle: an SDK build, a re-export, a MotionWorks compile, an Optix build. A read-back check catches a write that landed differently.

The installed app is not a workspace

The bundle runs inside AryaCode. It never edits the installed application under %LOCALAPPDATA%\Programs\AryaCode, it never edits the app.asar, and it never rewrites a profile's package.json to work around a bug. Development and testing happen on a Dev AryaCode home, never on the installed instance.

When a fix seems to need a change to the installed shell, that is the signal the change belongs upstream in the harness, not here.

The backup tree

One place holds undo material: <workspace>/backups/<product>/<subject>/<UTC stamp>/, with backup-manifest.json listing every file and its SHA-256. MotionWorks keeps its attached-project records under .motionworks/attached/records/ because the IDE owns that layout; migration and PLC-5 write nothing and therefore back up nothing.

Vendor bytes and the network

Vendor help pages and vendor sample projects are never committed. Fixtures are either synthetic, authored by the repository, or generated on the owner's machine and kept local. The bundle makes no network call in a normal session; the only network use is a live-controller or bridge connection the user configured, and a network block in the drill suite proves the rest still works.

When in doubt

If a call would change anything a person cares about - a controller, a live project, a shared file - stop and ask. The bundle's job is to make that decision visible, not to make it quietly.

Troubleshooting

The first checks when a row, tool, bridge or built artifact is missing.

Audience: Anyone stuck

A row or tool is missing

  1. Check whether the row is switched on. PLC-5 and SLC 500 ship off by default; a profile that switched a row off gets no tools from it. The settings face reports the mounted rows. (The ECAD row that earlier releases shipped off has been retired; its drawing preview remains on the viewers row.)
  2. Check the build. The tools come from the installed bundle version. package.json names the version; the workbench shows it. A profile that kept an older copy of the bundle shadows the new payload.
  3. Check the product install. Product rows need their vendor software for parts of their surface: Studio ME for FTView export/import, Studio 5000 plus the SDK for L5X builds, Optix Studio for the bridge, MotionWorks IEC for the IDE path, RSLogix 5 for the PLC-5 vendor path. A capability or status tool names what is missing; a read path that parses files may still work.

A documentation lookup fails

  • SOURCE_NOT_INSTALLED means the vendor help the collection describes is not on this machine. The error names the roots it searched; install the help or use the authored corpus.
  • NOT_FOUND carries the closest ids. The page exists in the index only if the vendor help was indexed at build time.
  • REVISION_UNVERIFIED and INSTRUCTION_NOT_IN_REVISION are honesty guards, not failures to work around. Name the revision or accept the generic page.

The generator fails

python scripts/gen-handbook.py --check verifies the Markdown sources and built artifacts. Common causes:

  • a page is missing title, order, purpose or audience front matter, or two pages share an order;
  • the built files are stale relative to the sources (run the generator);
  • PDF rendering cannot find Chrome or Edge. The HTML and DOCX still build; the PDF step exits with a message naming the missing browser.

A preview is blank

A drawing or display preview renders a local file. A blank face usually means the file did not parse, the display is empty, or the browser needed for PNG rendering is missing. SVG output needs no browser; PNG does.

A vendor step is pending

The bundle produces plans and drafts; Studio and the IDE still act. If the next step is "open Studio and use the import wizard", that is expected, not a failure. The handoff tool lists the exact steps.

Reporting a problem

Include the row, the tool, the error code, the version and what was installed. The error envelope's fix field usually names the next check; the product page's limits section says whether the case is known.

Known gaps and what is not proved

The claims this release does not make, by product, so no reader mistakes beta for finished.

Audience: Reviewers and release engineers

Every component is beta

Every row and support component in this bundle is beta, and every component records a stabilityNote saying what is not proved. Beta means the surface is tested and usable; it does not mean every vendor version, controller family or host combination has been measured.

MotionWorks IEC

The repository records live evidence for the MotionWorks IEC 3 Pro 3.x line (3.0.3–3.7.5) against a staged copy of a real project on 2026-10-23, but that evidence was recorded on a host with the IDE. This host has no MotionWorks IEC install with a reachable bridge, so on this machine the compile, live-IDE and profile paths are unproved and fixture-tested only. Other IDE versions, controller families, downloads and the real-workspace write path are unmeasured.

FactoryTalk View

One ME export has been measured. The alarm decoder covers 34 of 66 applications on the recorded host, tag decoding 64 of 66, with the reason written into export warnings. The Studio import step, other ME versions and a second application are unmeasured. SE is a documentation source, not a product row.

Studio 5000 L5X

The recorded SDK verification is a 37.11 build with zero errors plus a neutral-text paste; the current host has Studio 5000 v37.05.00 and SDK 2.02.00, and the build is re-verified locally as part of this work. Instruction, revision and controller coverage beyond the recorded case is unmeasured. FBD and SFC execution semantics are not exercised. l5x_export_acd_to_l5x output can be refused on re-import.

Optix and NetLogic

Two steps stay manual: compiling the bridge class and running StartBridge. A save is not a build, and a rendered screen is a preview of the saved project. The bridge has been exercised on Studio 1.8.1.27 with a system .NET 8 and on a 1.7.4.32 emulator.

Legacy migration and PLC-5

Migration's instruction map covers 58 mnemonics with citations; uncovered instructions are review items. The wizard cannot emit newer than it ships, so a build proof needs a retarget first. PLC-5 was measured on one .RSP through both paths; data-file values, point cards and online state are outside the row.

SLC 500

The row is new. Its .SLC text grammar and its automation boundary are covered by repository fixtures, including a redacted transcript, but a full project read from an owner-licensed RSLogix 500 session is still the evidence that closes real-project coverage. The row ships off, writes nothing and never goes online.

ECAD

The product row is retired; the read-only drawing preview stays. Electrical authoring is AryaCAD Electrical's job, not the bundle's.

Evidence and the repository

The authoritative list is the capability page (docs/capabilities.md) plus each product page's Limits section. Generated figures that are stale against the current release - for example screenshots from the previous preset layout - are replaced by the release that changes them. The generated tool reference excludes the 32 vendored Optix tools by design, so a missing Optix row there is not a missing tool.
