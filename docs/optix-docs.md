# Optix help: the installed documentation as a searchable local index

Studio ships its own documentation next to the IDE: on 1.8.1.27 that is 2,591 HTML pages,
266 MB, generated by DITA from the same source Rockwell's AI assistant is grounded on. The bundle
ships what a search needs from them — page id, title, section, headings and a 320-character snippet
— and reads the full page from the install when someone asks for one. That is the whole knowledge
layer: a file, a few regexes and a ranking rule, with no model, no embedding database and no service
to keep running.

## Why an index and not the pages

| | |
|---|---|
| Pages on disk | 2,591 HTML files, 266 MB, under `<Studio>\Help\en` |
| Shipped index | one JSON file, 2,591 pages, 1,354 KiB, generated by `node scripts/gen-optix-help.mjs` |
| Refresh | `node scripts/gen-optix-help.mjs` after a Studio upgrade; `--check` fails when stale |
| Runtime need | searching needs nothing installed; reading one page needs the Studio the project runs in |

The pages change when Studio is upgraded, so the index carries the Studio version it was built from
(`studioVersion: "1.8.1.27"`) and `optix_docs action status` compares that with the installed
`IDEVersion.txt`. A stale index still answers, but `status` says so and names the regeneration
command, because a search that quietly describes the previous release is worse than one that admits
it.

## The tool

```
optix_docs({ action: "search" | "read" | "status", query?, id?, section?, limit? })
```

- `search` tokenises the query, requires at least one token to appear in the title, headings, id or
  snippet, and ranks: an exact title phrase is worth 100, a title token 25, an id token 6, a heading
  8, a snippet 2, plus 20 when every token matched. The page named after the thing asked about wins,
  which is almost always the right page.
- `read` returns one page as text: headings, paragraphs, list items, with the site navigation chrome
  cut away (the extractor starts at `#wh_topic_body`, so "Jump to main content" and the footer never
  become documentation).
- `status` reports the indexed page count and Studio version, the install it would read from, whether
  that folder exists, and whether the index is stale.

Result shapes are the same envelope as every other tool: `summary`, `data`, `coverage`, `next`.
A search returns at most `limit` hits (default 8) with a snippet each; nothing here can quietly add
six figures of HTML to a conversation.

## What it is evidence for, and what it is not

The help is evidence for **Rockwell's documented behaviour**: an API name, a member list, a menu path,
a property's stated meaning. It is not evidence about the project in front of you — the model, the
bound tags and the current values come from `optix_read`, `optix_schema` and the bridge.

It is also incomplete, and the gaps are worth knowing:

- **`ChangePanel` is not in the installed help at all.** A search for it returns zero pages on
  1.8.1.27, even though it is the method every panel switch calls. That is why navigation has its own
  page ([Optix navigation](optix-nav.md)), its own corpus page
  (`packages/resources/corpus/optix/optix-navigation-patterns.md`) and its own tool
  (`optix_nav`): the sample projects, not the reference, are the source for that idiom.
- The help names UA data types in places where the runtime reports CLR types; `optix_schema` records
  that split rather than hiding it (`datatype_drift` in `action refresh`).
- Template-library types (for example `NavButton`, `AlarmManagerButtonIcon`) are documented by the
  library that ships them, not by the Help folder, so a "type not found" answer from the help is not
  a claim that the type does not exist.

## Order of research

1. `optix_docs action search` with the API name or menu label — one call, ranked, snippet each.
2. `optix_docs action read` on the page that matches — the full text, from the install.
3. `optix_schema` for this Studio build's object model, enums, properties and `clrType` names.
4. `optix_read` / `optix_netlogic` for what the live project actually holds.

## Tests

`test/optix-help.spec.mjs` pins the extractor (body cut at `#wh_topic_body`, script and nav text
never leak), index building on a temporary Help tree (engine folder skipped, ids and sections
derived from paths), the ranking rule, section filtering, the refusal of an empty query, page reads
against a temporary install, staleness reporting, and two facts about the shipped index: every
listed page carries the fields a search needs, and `ChangePanel` genuinely is not documented.
